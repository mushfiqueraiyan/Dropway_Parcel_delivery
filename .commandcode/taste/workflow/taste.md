# Workflow

- When asked to build a design/UI, wants the visual design delivered as pure static markup — strips out client-side interactivity and runtime "logic" (useState, handlers, fake data states) rather than shipping interactive machinery. Confidence: 0.65
- Communicates frustration bluntly when work drifts from the ask (e.g. "i want the design not fucking logics"); prioritize delivering exactly what was requested over adding unrequested functionality. Confidence: 0.5
- Expects UI work to reflect the product's real domain and user roles (e.g. customer-facing booking + admin/dispatch views); issues corrective feedback when the agent builds a generic industry archetype instead of matching the actual product. Confidence: 0.5
- Wants UI copy/content localized to the product's real market (Bangladesh) — local areas/districts (Gulshan, Banani, Dhanmondi), ৳ BDT pricing, +880 phone numbers, bKash payouts, and local names — instead of generic placeholder content. Confidence: 0.55
- Prefers new pages/components to mirror the structure, state pattern, and styling of existing analogous pages in the codebase (e.g. "look at the login page now make like this for register page") — consistency with established conventions over inventing a fresh layout. Confidence: 0.6
- When asking to "design" a page that already exists functionally, means restyle it onto the app's established visual system (tokens, typography, shared shells) scoped to the UI — underlying business logic/API calls stay intact. Wants a "professional" result that is driven by the real data shape ("design the /track page according to data ... just professional design"). Confidence: 0.65
- Prefers repeated UI patterns extracted into shared, reusable components (layout shell, labeled text field) so sibling pages stay visually consistent instead of duplicating markup. Confidence: 0.55
- When reporting a runtime error (e.g. an HTTP 500 on an API route), wants a direct root-cause answer plus the fix actually applied and demonstrated in the terminal (real commands run to reproduce/verify), not a prose-only walkthrough. Confidence: 0.55
- Asks for terse responses on focused questions ("just answer this") — answer the specific question rather than expanding into a broad explanation or unrelated changes. Confidence: 0.5
- Just do the task directly, not unusual/ad-hoc shell work ("just do the task dont ususual shell work", "finish it quickly no unsual shell task", "stop unusual shell task just solve issue", "no unusual shell work just professional design and solve error if any quickly", "please solve no unusuall shell task") — prefer the standard, obvious path and avoid extra exotic one-off commands or meandering shell exploration. Also means skipping setup/verification ceremony (e.g. installing browser automation or other supporting tooling first) and applying the requested fix immediately when told "please just solve it". Confidence: 0.85
- Cut long diagnostic detours short: when extended investigation/scratchpad probing drags on, wants the agent to either commit to a concrete fix and apply it or drop the issue entirely ("please stop just solve it or leave it") — no further explanation of theories in place of action. Confidence: 0.6
- Expects tasks driven to full completion ("finish the task solve all error") — resolve every outstanding error and reach a verified working state before stopping, rather than reporting partial progress or handing back a task with known failures. Confidence: 0.55
- Make minimal, scoped edits to existing files: preserve the user's working code (data fetching, state, types, component name) and only touch the part being asked about — never rewrite or replace a whole file the user already wrote. Gets angry when existing working logic is destroyed during a UI task ("you did destroyed all code"). Confidence: 0.7
- When asking for a redesign ("redesign the homepage", "change the full design"), expects a fundamentally new composition/layout and visual language — not the existing structure with reskinned styling. Rejects a "same but tweaked" result and will push back ("looks like new home page not this one same"). Confidence: 0.65
- On such redesigns, expects the established brand color palette/design tokens (and fonts) kept intact while everything else changes — "just maintain the colors, change full looks, remove current design". Confidence: 0.55
- For marketing/landing pages, wants a bright, app-first delivery look modeled on the reference products they name (e.g. Pathao/Uber), not an internal ops-console/technical aesthetic. Confidence: 0.5
- After a redesign, expects the new visual language rolled out consistently across the app's other pages (prompts page-by-page, e.g. a bare "now the add-parcel page" right after the homepage rewrite), each sibling page restyled into the same system while its existing logic is kept. Confidence: 0.55
- Scopes requests tightly to the named feature/files and expects the agent to stay inside that boundary ("dont change anything or any code just implement ... in add-parcel page and api") — don't cascade the change into other files or "fix the whole build" unprompted even when unrelated files are broken by it. Confidence: 0.55
- Often makes their own partial edits first and expects the agent to inspect that in-progress state (e.g. "I already applied something on that also in prisma schema you can check no unusual shell task") and finish/build on top of it rather than redoing or reverting it. Confidence: 0.5
- When adding new content/sections to a page, wants the existing design untouched ("dont change any design or code add these section") — add the new UI reusing the existing markup/classes so the look is unchanged rather than restyling anything. Confidence: 0.55
- Expects new feature work to start by reading the existing related API route and Prisma model/schema and implementing the page + endpoints to match them ("look at the rider api and model Rider schema do according to it") — align new code to the established data model rather than inventing fields. Confidence: 0.55
- Wants cross-cutting behavior enforced at the data/API layer too, not just surfaced in the UI (e.g. a rider application going `active` should also promote the user's role: "do that also in schema"). Confidence: 0.5
- For admin/dashboard screens, prefers a table layout (one row per record) with the row action button (e.g. Assign/Manage) aligned to the right, plus a left sidebar for navigating the other dashboard sections rather than a stack of cards. Confidence: 0.55
- For admin records, wants the row clickable to open a popup/modal showing the record's full details with the state-changing action (e.g. activate/deactivate) inside that popup, rather than a separate detail page. Confidence: 0.5
- Surfaces status subsets as their own sidebar entry + page (e.g. a "Pending riders" page listing all non-active riders) instead of a filter control on the main list. Confidence: 0.5
- Wants dev/demo data seeded with full coverage of the real domain (e.g. 1-2 active riders for every district/upazila) generated in bulk and fast (calls out a time budget like "in 10sec"), rather than a handful of sample records. Confidence: 0.5
- Expects seeded/demo records (and existing DB rows) to hold realistic, valid values rather than junk/placeholder data — will ask to rewrite them in bulk ("change all rider names from the database to a valid name") and wants the generated values to look genuine (e.g. plausible local names). Confidence: 0.5
- Reports problems by pasting raw terminal output verbatim (command + full error text, sometimes with IDE file/line context) instead of describing the issue in prose — expect to parse the raw log to identify the failing step, then answer "what is this issue" with the actual cause. Confidence: 0.65
